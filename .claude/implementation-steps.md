# Implementation steps: biopsy sampling-site finder

Build plan for the Ashby Hackathon (UIUC) web app, written 2026-10-17 from the team's project brief. Use `project` as the package and folder name until the team picks a name.

The app: a user uploads a photo or scan of a biopsy slide. The backend tiles it, scores each tile with CONCH, and ranks regions. The results screen draws boxes around the **top 5 regions to sample** and marks the best one. Clicking a box explains that region: its cell composition, why it was chosen, and how it compares with the other regions. It must look like a finished product, not a template.

**Stack in one line:** a Next.js frontend talks to a FastAPI service, and all the ML logic (ingest, tiling, CONCH, ranking) stays in Python behind it.

## 2. How to work

1. **Tests first in every phase** (AGENTS.md §2). Write the tests, run them, and confirm they fail for the right reason (missing function or wrong value, not a syntax or import error). Then implement until they pass.
2. Never weaken, skip, `xfail` or delete a test to get a pass. The thresholds this file sets (AUROC ≥ 0.8, contrast ≥ 3:1, the tolerances) don't move.
3. Don't stop for review between Phases 0–7. Make reasonable decisions yourself and log each one in `reports/decisions.md`: one line, decision + reason.
4. **A phase is done** when its tests and the whole `make test` suite pass and it's committed as `phase N: <summary>`. Don't start a phase while the previous one has failing tests. Work on a branch (e.g. `build/app`), not `main`. Stage only the files the phase touched (no `git add -A`). Don't push without approval.
5. After each commit, print the short report CLAUDE.md asks for (tests added, pass/fail counts, any number and the file it came from, next step), then carry on.
6. `make test` must pass with no GPU, no internet and no Hugging Face token, using `FakeBackend`. The backend part runs in under 60 s (AGENTS.md §7). Fixtures are synthetic and small. Never commit a real slide or anything over 5 MB (AGENTS.md §3).
7. Every random choice takes its seed from `config.yaml` (AGENTS.md §3). Every metric gets a hand-computed test with the expected number written in (AGENTS.md §7): contrast ratio, AUROC, region score, and in Phase 8 MAE, Pearson r and the bootstrap.
8. Don't invent library APIs. For CONCH, OpenSlide and FastAPI, read the installed package's source or the official docs. For Next.js, read the guides bundled with the installed version in `frontend/node_modules/next/dist/docs/`: Next 16 differs from older versions.
9. Never read, print or log `.env` or a token (rules.md §8). Never `Read` or `cat` slides or large data files (CLAUDE.md).
10. **Time target: about 1.5 hours for Phases 0–7.** Get speed from simple code (the simplest code that passes the tests, few dependencies, no extra abstractions), never from skipping tests.

## 3. Stack and where it runs

- **Backend (Python):** FastAPI, Pillow, NumPy, OpenSlide (for .svs/.tiff scans), CONCH via its official loader, pytest. All the ML logic lives here: ingest, tiling, tissue detection, CONCH scoring, region ranking, reasons and the heatmap. Pin versions.
- **Frontend (Next.js):** Next.js 16 (App Router) + React 19 + TypeScript + Tailwind CSS 4, in `frontend/`. Vitest + React Testing Library for components, Playwright for the end-to-end flow. Pin versions. The frontend holds no ML: it uploads, polls and draws what the API returns.
- **How they talk:** the browser only calls Next.js. `frontend/next.config.ts` rewrites `/api/*` to FastAPI at `API_URL` (default `http://localhost:8000`), so there's one origin and no CORS. `API_URL` is read when `next dev` or `next build` starts; a built app keeps the value it was built with.
- **Upload size:** Next buffers proxied request bodies and cuts them off at 10 MB by default. `next.config.ts` sets `experimental.proxyClientMaxBodySize` from `max_upload_mb` in `config.yaml`, so uploads up to that size reach FastAPI whole. Keep it that way.
- **Node:** Next 16 needs Node ≥ 20.9. Vite stays pinned at 6.4.4 as a dev dependency because Vitest runs on it, and Vite 7 needs Node ≥ 22.12.
- **Device:** picked automatically, in order: CUDA, Apple MPS, CPU.
- `FakeBackend` runs anywhere. `ConchBackend` runs on the laptop of a teammate who has their own CONCH access (rules.md §5), or in a Delta GPU job. Never on the Delta login node (rules.md §1). On compute nodes, pre-fetch the weights and set `HF_HUB_OFFLINE=1` (AGENTS.md §5).
- The hosted CONCH server only answers from inside Delta (rules.md §6), so the app must not depend on it.

## 4. Contracts

### Model backends
- `ModelBackend` interface: takes a batch of tiles, returns an `[n_tiles, 6]` array of class probabilities. Columns follow the class order in `config.yaml`, and each row sums to 1.
- `ConchBackend`: real CONCH image embeddings + zero-shot class scores. Load it as AGENTS.md §5 says: `create_model_from_pretrained("conch_ViT-B-16", "hf_hub:MahmoodLab/CONCH")`, then `.eval()`, and run under `torch.no_grad()`. Image embeddings use `proj_contrast=True, normalize=True` (AGENTS.md §4). Text embeddings come from the prompts in `config.yaml`. Check the installed `conch` package for the tokenizer and text-encoding functions.
- `FakeBackend`: deterministic scores computed from tile color, for tests and offline work.
- `config.yaml` sets `model: conch | fake`. If `model: conch` and the token or weights are missing, the server refuses to start with a clear message naming what's missing (never the token's value). **Never fall back to the fake model silently**, because the app would show made-up results as real ones.
- "Token present" means `HF_TOKEN` is set. If the team runs on Delta with `hf auth login` instead, also accept the token that login cached (look up how in the installed `huggingface_hub`) and log the choice.

### Tissue classes
`tumor, stroma, immune, necrosis, normal, fat_other`, zero-shot, prompts in `config.yaml`. Each tile gets a probability for each class, summing to 1.

### Region scoring (weights in config)
- A region is an N×N block of tiles (N = 4 by default, set in config).
- `composition` = mean class probabilities over the region's tiles.
- `score = tumor − w_necrosis × necrosis − w_variation × std(tumor across tiles)`.
- A region is eligible only if `tissue_coverage ≥ min_coverage` (no blank glass, no tissue edges).
- Return the top 5 non-overlapping eligible regions, ranked by score. Simplest way: slide the N×N window one tile at a time, take the best, drop the candidates that overlap it, and repeat. If fewer than 5 are eligible, return what exists and set `note` to explain why.

### Reasons (rule-based, never generated by an LLM)
Every reason is built from the region's own numbers and quotes them. Emit a reason only when it's true: "Highest tumor content" only if no other eligible candidate has more, and the "low necrosis" and "low variation" cutoffs live in config. Format percentages in one helper so the tests can parse them back. Examples:
- "Highest tumor content of all candidates (62%)"
- "Low necrosis (3%), which favors good DNA yield"
- "Fully on tissue (98% coverage)"
- "Tumor content is even across the region (low variation)"
- For ranks 2–5: "Tumor content is 8 points lower than the best region"

### API
FastAPI serves these routes. The browser calls the same paths on the Next.js origin, and the rewrite forwards them (§3).
- `POST /api/jobs` (multipart: `file`, optional `mpp`) → `{ job_id }`. The brief's path was cut off; `/api/jobs` matches the other routes.
- `GET /api/jobs/{job_id}` → `{ status: queued|running|done|error, step, progress (0–1), model, result?, error? }`
- `step` is one of: `finding_tissue`, `tiling`, `analyzing`, `ranking`.
- `GET /api/jobs/{job_id}/display.png` and `GET /api/jobs/{job_id}/heatmap.png`.
- Uploads: accept .png, .jpg, .jpeg, .tif, .tiff, .svs up to `max_upload_mb` (config). A wrong type or a corrupt file returns 400 with a readable message, a file that's too large returns 413, and an unknown job id returns 404. A blank image ends the job in `status: error` with "No tissue found in this image."

### Result JSON
```json
{
  "model": "fake",
  "image": { "url": "/api/jobs/{id}/display.png", "width": 2048, "height": 1536, "mpp": 0.5, "mpp_estimated": false },
  "heatmap_url": "/api/jobs/{id}/heatmap.png",
  "tiles": { "count": 412, "capped": false },
  "slide_composition": { "tumor": 0.41, "stroma": 0.30, "immune": 0.12, "necrosis": 0.05, "normal": 0.08, "fat_other": 0.04 },
  "regions": [
    {
      "rank": 1, "is_best": true,
      "x": 812, "y": 440, "w": 256, "h": 256,
      "score": 0.58, "tissue_coverage": 0.98, "tumor_std": 0.06,
      "composition": { "tumor": 0.62, "stroma": 0.21, "immune": 0.09, "necrosis": 0.03, "normal": 0.03, "fat_other": 0.02 },
      "size_um": 512,
      "reasons": ["Highest tumor content of all candidates (62%)", "..."]
    }
  ],
  "note": null
}
```
- Box coordinates are in pixels of the **display image** (the downsampled PNG the browser shows), not the original scan. Keep the display-to-original scale factor internally.
- `image.mpp` is the original image's µm/px. `size_um` = N × `tile_px` × `target_mpp`, or null when the image scale is unknown. In the example, a 256 px box is 512 µm because the display is downsampled 4×.
- Fields added to the brief's schema, each logged in `decisions.md`: `model` (drives the "Demo model" badge), `image.mpp_estimated` (true when mpp came from the user or the config default), `heatmap_url` (for the overlay toggle), and `tiles` (records when `max_tiles` was hit).

### Phase 1: Image ingest and tiling (backend)
**Tests first** (synthetic images, made in the test or saved as tiny fixtures)
- Supported files load. Unsupported and corrupted files raise an error that the API turns into a 400 with a message.
- A synthetic white image ends in "No tissue found in this image."
- Tissue detection: a white tile has tissue fraction < 0.05; an H&E-pink tile has > 0.8.
- Every tile lies fully inside the image bounds.
- For scans with known mpp, tiles are cut at `target_mpp`. For plain photos, use the `mpp` the user entered, or the config default, and mark the scale as estimated.
- The display image is ≤ `max_display_px` on its longest side, and the scale factor maps display pixels back to original pixels correctly.

**Build**
- Ingest (OpenSlide for .svs and tiled TIFF, Pillow for the rest), tissue mask, tile grid, and the display image with its scale factor.
- OpenSlide needs its C library. Try the `openslide-bin` wheel first, else `brew install openslide`. Confirm the import works and log which one you used.
- A real .svs can't be a committed fixture (size and patient data, AGENTS.md §3). Cover the OpenSlide path with a tiny generated tiled TIFF or a stubbed reader, and log which.

### Phase 2: Tile model
**Tests first**
- Class probabilities per tile sum to 1 (atol 1e-5).
- Output rows match the number of tiles.
- Same tile in, same scores out (eval mode, no grad).
- `FakeBackend` is deterministic and gives a pink-purple tile a higher tumor score than a pale tile.
- With `model: conch` and no `HF_TOKEN`, server startup fails with a clear message. With `model: conch` and a failed load, it raises instead of returning `FakeBackend`.
- When tiles exceed `max_tiles`, exactly `max_tiles` are kept, spread evenly across the tissue, and the cap is recorded.
- AUROC helper: a small NumPy function (no scikit-learn), checked against a hand-computed example.
- `@pytest.mark.realmodel`: the same-tile determinism check on real CONCH.
- `@pytest.mark.realmodel` accuracy check: 200 tiles sampled with the config seed from the public CRC-VAL-HE-7K tile set (Kather et al., Zenodo record 1214456), tumor (`TUM`) vs. rest, AUROC ≥ 0.8. It writes `results/conch_auroc.json` (AUROC, tile count, seed, prompt set).

**Build**
- `ConchBackend` and `FakeBackend`, with tiles batched.
- Cap tiles per image at `max_tiles` by sampling evenly across the tissue, and record when the cap is hit.

**CRC-VAL-HE-7K**
- The test reads it from a path set in `config.yaml`. On Delta, look in `/projects/bfqi/shared/datasets/` first and read it in place (rules.md §4). Otherwise write `scripts/get_crc_val.sh`, and check the download size first: anything over 1 GB needs approval (CLAUDE.md).
- If the data isn't there, the test skips with a message naming the config key and the script.
- Never open its tiles with `Read` (AGENTS.md §6).
- If AUROC < 0.8, adjust the prompts in config **once**, rerun, and keep both results for `final.md`. The 0.8 bar doesn't move. If it still falls short, the test stays red and the report says so.
- The realmodel tests run in Phase 7, not now.

### Phase 3: Region ranking and reasons
**Tests first** (synthetic score grids, no images)
- One high-tumor square patch in a synthetic grid → the top region lands on it.
- Exactly 5 regions when ≥ 5 are eligible; fewer, with a `note`, when not.
- Regions never overlap, and all have coverage ≥ `min_coverage`.
- Exactly one region has `is_best: true`, and it is rank 1.
- Ranks are sorted by score, descending.
- Each region's composition sums to 1.
- Every number quoted in a region's reasons matches that region's data (parse the percentages back out and compare).
- A high-necrosis region loses to a slightly lower-tumor, low-necrosis region when the necrosis weight says it should.
- The score formula matches a hand-computed example.
- Heatmap orientation: a value placed at tile (x, y) lands at `array[y, x]` (AGENTS.md §4).

**Build**
- Ranking, rule-based reasons, and the tumor heatmap PNG at display size for the overlay toggle.

### Phase 4: API
**Tests first** (FastAPI test client, fake model)
- Upload → job → poll until `done`; the result validates against the Result JSON (as a Pydantic model).
- `step` and `progress` move forward and never go backwards.
- Bad file type → 400; file too large → 413; unknown job id → 404.
- A blank image ends in `status: error` with the "No tissue found" message.

**Build**

Check the type and decode the file during upload (400 right away), and check the size while reading it (413). Run the Phase 2 startup check when the app starts. ### Phase 5: Design system
Read `.claude/skills/frontend/ui-design/SKILL.md` first. No skill named "frontend-design" is installed, and this is the closest. (The agent files in `.claude/agents/` point to `~/.claude/skills/general/…`, which doesn't exist; use the repo paths here.)

**Tests first:** a Vitest unit test that computes the box contrast ratios from the tokens (read from `frontend/app/globals.css`) and fails below 3:1, plus a hand-computed check (black on white = 21:1).

**Build** `frontend/DESIGN.md` and the design tokens before any screen.
- **Direction:** a calm, clinical-precision look that lets the slide image be the hero. One display font and one body font, a neutral base, and one accent. No default Tailwind blue, no generic gradient-hero styling.
- **Fonts:** load them with `next/font/local`, from font files in the repo or an `@fontsource/*` package. Not `next/font/google` or a CDN: those need internet at build or run time, and tests must work offline with no console errors in Phase 7.
- **Tokens:** colors, type scale, spacing, radii, shadows and motion durations live in one place: the `@theme` block in `frontend/app/globals.css` (Tailwind 4 has no `tailwind.config` by default). Components use tokens only, no one-off hex values.
- **Light and dark mode.**
- **Box colors:** each box style needs contrast ≥ 3:1 against both eosin pink `#E8B4C8` and hematoxylin purple `#6B4C9A`. The best box must also stand out without color: a thicker stroke plus a "Best" label.

**Do the contrast math before picking colors.** Pink's relative luminance is about 0.540 and purple's about 0.106. A single solid color reaches 3:1 against both only if its luminance is ≤ 0.002, which means near-black: `#000000` gets 3.13:1 on purple, and `#0A0A0A` already fails at 2.95:1. So two distinguishable one-color box styles can't both pass. Draw each box as two strokes: a black outer outline and a colored inner stroke (the accent for the best box, a light neutral for the others). The test checks, for each box style and each tissue color, that at least one stroke layer reaches 3:1. Log this in `decisions.md` and explain it in `final.md`. It changes how the test reads the requirement, not the 3:1 bar.

### Phase 6: Frontend screens
Read `.claude/skills/frontend/ux-thinking/SKILL.md` first (states, errors, copy).

**Structure (Next.js App Router)**
- Routes: `/` (home), `/upload`, and `/jobs/[id]`, which shows Analyzing while the job runs and then Results. A results URL survives a reload.
- Pages stay Server Components. Anything with state, effects, polling, drag-and-drop or click handlers is a Client Component (`'use client'`). Use `not-found.tsx` for an unknown job id (the API's 404).
- Show the slide with a plain `<img>` whose `width` and `height` come from the result. It's a per-job PNG from the API, so the image optimizer adds nothing, and the boxes must scale with its rendered size.
- `default_mpp` and `max_upload_mb` come from `config.yaml`: read them in `next.config.ts` and pass them to the client through `env`.

**Tests first** (Vitest + React Testing Library, with `fetch` and `next/navigation` mocked)
- Home: a clear headline, a one-line explanation, and a primary "Analyze a slide" button that opens the upload screen.
- Upload: drag-and-drop plus a file picker; shows a preview; an optional "Image scale (µm/px)" field with the default filled in; rejects unsupported files, and files over `max_upload_mb`, with an inline message before uploading.
- Analyzing: shows the four steps (Finding tissue → Tiling → Analyzing with CONCH → Ranking regions), highlights the current one, and shows the error state with a "Try another image" button.
- Results: renders exactly as many boxes as regions, with rank badges 1–5; the best box uses the best color and the "Best" label.
- **Box scaling:** with a 2048 px wide result shown at 1024 px, a region at x = 800 is drawn at 400 px. Check again after a window resize. (Mis-scaled boxes are the classic bug here.)
- Clicking a box, or pressing Enter on it, opens the detail panel for that region and marks the box as selected. Clicking another box switches the panel.
- Detail panel shows: rank and score; a **cell composition** stacked bar with percentages for all six classes, with the note "Estimated from tile classification, not individual cell counts"; the reasons list; this region's tumor % vs. the whole slide; size and tissue coverage.
- The API's `note` is shown when fewer than 5 regions came back.
- A visible "Demo model" badge when `model` is `fake`, and none when it's `conch`.
- The one-line research-use notice is on the results screen.
- Size is labeled as estimated when `image.mpp_estimated` is true.

**Build**
- The four screens, with polish: smooth transitions between screens, hover and focus states on boxes, a toggle for the tumor heatmap overlay, and a "New analysis" button on results.
- Show the "Demo model" badge on the Analyzing screen too, since its step label names CONCH.
- Layout works at 375 px and 1440 px widths.

- Then write `reports/final.md` (§6 below).

### Phase 8 (optional): Validation on TCGA
Start only after Phases 0–7 are complete and committed. Goal: show that the tumor signal tracks real purity. On TCGA slides from hospitals held out by tissue-source-site code, compare the app's whole-slide tumor estimate and the pathologist's estimate against ABSOLUTE purity.

This is AGENTS.md's pipeline territory, so follow it:
- Build `labels.csv` in the AGENTS.md §4 format, with every AGENTS.md §8 Phase 1 test. The key one: no `hospital` appears in more than one split. Convert ABSOLUTE fractions to percent once.
- App estimate = `slide_composition.tumor` × 100. If you fit any mapping from it to purity, fit it on training hospitals only.
- Compute MAE and Pearson r for the app **and** the pathologist on the same test slides, plus the 60% catch rate (AGENTS.md §1). Each metric gets a hand-computed test (AGENTS.md §8 Phase 5).
- Bootstrap the test slides 1,000 times (seeded). Call the app "better" only if the 95% interval of (pathologist MAE − app MAE) excludes 0; otherwise call it "comparable". Report the interval with the claim.
- Use TCGA open-access data only (AGENTS.md §6). Slides live under `/work/nvme/bfqi/<username>`, whole-slide inference runs only in approved GPU jobs, and large downloads need approval (CLAUDE.md, rules.md §3–4).
- Write the numbers to `results/tcga_validation.json` from code, and generate the README results table from that file (AGENTS.md §9). Every number names its split and slide count.
- A result that looks too good is a bug until proven otherwise (AGENTS.md §2). CLAUDE.md allows one fresh subagent to re-derive the headline numbers, and the audit checklist in `.claude/agents/ml-engineer.md` fits this phase.
